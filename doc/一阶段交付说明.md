# MTSCO 企业内部知识库一阶段交付说明

> 面向领导审批和发布会汇报使用。本文以当前代码、数据产物、接口能力和测试记录为主要依据；历史方案文档仅作为背景参考。正式发布前，准确率、成本等仍需以最终跑分和线上账单口径替换。

## 一、汇报建议

### 1. 建议重点讲什么

领导关注的不是系统用了什么技术，而是这个系统能不能解决实际问题、是否值得开放试用、后续需要哪些资源支持。因此汇报建议围绕以下主线展开：

| 汇报重点 | 建议表达方式 | 领导能判断的问题 |
| --- | --- | --- |
| 项目价值 | 员工可在飞书里直接提问，系统根据公司资料回答，并给出资料来源 | 是否能减少重复咨询和资料查找成本 |
| 一阶段结论 | 主链路已跑通，具备小范围试用和演示条件，测试数据仍在最终跑分 | 是否可以进入审批和试用 |
| 实际效果 | 展示真实问题、真实回答、来源链接、停止回答、反馈入口 | 是否像一个可用产品，而不是技术 Demo |
| 指标 | 回答耗时、准确率、资料覆盖、题集规模、并发测试、反馈机制、成本估算 | 是否可量化、可验收、可持续优化 |
| 风险边界 | 资料不全时会影响答案；敏感资料需要权限策略；准确率仍需业务题集验证 | 是否知道风险、是否有控制手段 |
| 需要支持 | 资料负责人、题集审核人、试用范围、服务器和模型费用预算 | 需要领导协调什么 |

### 2. 不建议重点讲什么

以下内容不适合在领导汇报中展开，最多放在附录或答疑里：

| 不建议展开 | 原因 | 可以替换成 |
| --- | --- | --- |
| 大段代码、接口参数、库名称 | 非技术领导难以判断价值 | “资料处理能力”“问答服务”“检索服务” |
| 模型、向量、重排等细节 | 容易把关注点带偏 | “先查资料，再组织答案，并按相关度筛选依据” |
| 开发过程中的报错和临时方案 | 容易显得项目不稳定 | “已完成若干稳定性和体验优化” |
| 未经验证的准确率承诺 | 审批后容易成为风险 | “目标不低于 80%，最终以正式题集跑分为准” |
| 过细的成本计算 | 当前成本受问题长度、模型选择、并发量影响 | “给出估算口径和试用期预算上限” |
| 过度宣传替代人工 | 容易引发业务抵触 | “辅助员工快速找到资料，减少重复询问” |

### 3. 发布会建议演示顺序

1. 先演示“普通员工怎么用”：在飞书中提问一个入职、培训或制度类问题。
2. 再演示“答案是否可信”：展示答案中的来源链接，点击回到原文档。
3. 再演示“系统是否知道边界”：问一个资料中没有或前提错误的问题，观察是否明确纠正或说明未查到。
4. 再演示“体验细节”：展示等待提示、停止回答、点赞/点踩反馈。
5. 最后展示“后台指标”：资料规模、题集规模、平均耗时、并发测试、准确率跑分结果。

演示问题建议提前准备 6 到 8 个，覆盖简单查询、流程类问题、口语化问题、错误前提问题、未覆盖问题和营销素材查询。不要现场随意开放无限制提问，发布会阶段更适合展示经过验证的代表性场景。

## 二、一阶段总体结论

企业内部知识库项目一阶段已经完成“从资料整理到飞书问答”的主链路建设，具备面向领导审批的实机演示条件，也具备进入小范围试用的基础。

当前完成情况可以概括为：

1. 员工可以通过飞书入口提问，系统可以返回自然语言答案。
2. 系统已能处理并入库多类公司资料，包括 Word、PDF、PPT/PPTX、Excel 及图片/链接等富内容。
3. 回答可以关联来源资料，用户可点击链接回到飞书原文档。
4. 已加入等待提示、停止回答、在线反馈等面向实际使用的体验功能。
5. 已建立测试题集和评测框架，最终准确率数据仍在跑分中。
6. 已做生产环境和测试环境拆分，并补充隐私保护、并发优化和稳定性修复。

结论建议表述为：

> 一阶段不再只是“技术链路可行”，而是已经形成了一个可演示、可试用、可持续优化的内部知识库问答版本。当前最主要的待确认事项，是用正式题集完成准确率跑分，并根据试用反馈继续扩大资料范围和优化答案质量。

## 五、实机演示建议

### 1. 推荐演示场景

| 场景 | 示例问题 | 展示价值 |
| --- | --- | --- |
| 新员工流程 | 新员工入职前，人事部门和学院一般提前多久沟通？ | 展示制度/流程类问答 |
| 操作流程 | 酷学院管理端某个操作流程怎么做？ | 展示 SOP 和步骤类回答 |
| 产品/素材查询 | 有没有某类 Flange 或 Control Line 的图片资料？ | 展示营销素材库价值 |
| 错误前提纠正 | 我看到某文件是张三负责的，对吗？ | 展示不盲从用户错误前提 |
| 口语化问题 | 那个 flange 表面图到底 7 张还是 8 张？ | 展示理解不标准表达 |
| 未覆盖问题 | 问一个资料库中没有的敏感或未知问题 | 展示不编造、知道边界 |

### 2. 演示时不要做的事

1. 不要现场打开代码或数据库。
2. 不要让领导随机连续追问大量未验证问题。
3. 不要承诺所有公司资料都已经覆盖。
4. 不要说“系统一定不会错”，应说“可追溯、可反馈、可持续优化”。
5. 不要用“替代人工”做主卖点，应强调“降低重复咨询和资料查找成本”。

## 六、当前风险与控制方式

| 风险 | 当前表现 | 控制方式 |
| --- | --- | --- |
| 准确率尚未最终确认 | 测试题集已建立，但跑分还在进行 | 发布前补齐最终评测报告 |
| 资料质量影响答案 | 旧资料、空文档、命名混乱、截图缺说明会导致回答不完整 | 建立资料负责人和版本确认机制 |
| 来源链接权限问题 | 用户点击来源可能受飞书权限限制 | 试用前确认资料空间权限和访问范围 |
| 敏感信息边界 | 人事、客户、报价、合同、账号权限等不适合直接开放 | 分阶段开放资料，建立敏感资料清单 |
| 高峰期响应速度 | 并发下部分请求可能超过 1 分钟 | 保留等待提示，继续优化流程和模型调用 |
| 用户信任建立 | 用户需要知道答案从哪里来 | 强化来源链接、反馈入口和错误复盘机制 |

## 七、下一阶段建议

下一阶段不建议单纯继续加功能，而应围绕“可推广试用”做收敛：

1. 完成正式跑分报告，明确是否达到 80% 准确率目标。
2. 选定 1 到 2 个部门小范围试用，收集真实问题和反馈。
3. 建立资料维护机制，每类资料明确负责人、更新时间和权限边界。
4. 对失败案例做闭环，优先优化高频问题和领导演示中暴露的问题。
5. 建立成本看板，统计每日问题数、模型调用量、平均耗时和费用。
6. 推进敏感资料分级，避免未授权信息进入通用问答范围。
7. 将“能回答”逐步提升为“回答稳定、来源清楚、错误可复盘”。

## 八、可直接用于汇报的简版正文

### 1. 项目定位

MTSCO 企业内部知识库项目的目标，是让员工可以在飞书中用自然语言提问，由系统根据公司内部资料自动查找依据、组织答案，并提供来源链接，减少重复咨询、资料查找和经验传递成本。

一阶段的重点不是一次性覆盖公司所有资料，而是先把资料处理、知识入库、问题检索、答案生成、来源追溯和质量评测这条主链路跑通，形成一个可演示、可试用、可继续扩展的第一版。

### 2. 当前交付结论

截至当前，一阶段主链路已经完成。系统已支持飞书入口提问，能够基于已整理资料生成回答，并提供来源链接。除最终测试数据仍在跑分外，资料处理、问答入口、来源追溯、用户反馈、停止回答、隐私保护、环境拆分等关键事项均已完成。

当前版本已经具备领导发布会演示和小范围试用条件。发布前建议补齐最终评测报告，将准确率、失败案例和成本估算作为审批附件。

### 3. 已完成能力

系统当前已完成以下能力：

| 能力 | 当前效果 |
| --- | --- |
| 飞书问答 | 员工可在飞书中提问并获得回答 |
| 多格式资料处理 | 支持 Word、PDF、PPT/PPTX、Excel 等常见资料处理 |
| 知识检索 | 可根据问题查找相关资料片段 |
| 答案生成 | 可将资料内容整理为较易读的自然语言回答 |
| 来源追溯 | 回答可关联原文档链接，方便核对 |
| 营销素材查询 | 营销资料已作为独立素材库处理 |

### 5. 实际效果

当前系统已经可以完成以下实际使用场景：

1. 员工询问制度、流程、培训安排、产品资料等问题，系统给出结构化回答。
2. 员工询问某份资料、图片或营销素材时，系统能定位相关资料。
3. 用户问题表达不标准时，系统仍能尝试理解真实意图。
4. 用户问题存在错误前提时，系统可以基于资料纠正，而不是顺着错误前提回答。
5. 资料中没有明确答案时，系统应说明未查到，避免编造。
6. 用户可以点击来源链接核对原文，也可以对答案点赞或点踩。

### 6. 审批建议

建议批准项目进入一阶段发布会演示和小范围试用，但正式扩大开放前，需要完成以下确认：

1. 输出最终准确率跑分报告，确认是否达到 80% 目标。
2. 确认首批开放资料范围，排除敏感资料。
3. 确认飞书资料权限，保证用户可以打开答案来源链接。
4. 确认试用部门、试用人数和反馈收集方式。
5. 设置试用期成本上限和使用量统计口径。
6. 明确资料维护负责人和问题反馈负责人。
